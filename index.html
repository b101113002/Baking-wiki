01｜問題與目標

為什麼需要 Agent？

資訊分散

網站欄位、單位與時間定義不一致。

容易漏資料

材料、設備、發酵或冷卻時間可能漏掉。

需要可追溯

每份食譜都保留原始網址與來源識別碼。

02｜統一資料結構

每份食譜要記錄什麼？

  • 名稱、作者、來源網址、查閱日期
  • 材料名稱、數量、單位與可選項目
  • 設備、產量、準備／發酵／烘烤／冷卻時間
  • 烤溫、逐步教學、成品判斷指標
  • 問題檢查、過敏原提醒與品質狀態
03｜Graph 流程

節點化處理

PLAN → SEARCH → FETCH → PARSE → NORMALIZE → VALIDATE → DEDUPLICATE → PERSIST → REPORT

節點接收共享 State 並回傳更新；條件邊決定下一步。

04｜迴圈與條件分支

失敗時不是硬猜

  • 來源讀取失敗：回 SEARCH 換來源。
  • 欄位格式錯誤：進 REPAIR，再重新驗證。
  • 來源缺資料：回 FETCH／SEARCH。
  • 重試最多 2 次；仍無法確認就標記 WARNING／FAIL。

06｜品質檢查

PASS / WARNING / FAIL

PASS

來源與核心材料、步驟足夠，沒有重大矛盾。

WARNING

可供參考，但仍有缺漏或待核對資訊。

FAIL

來源無效或核心資訊不足，不進正式食譜區。

08｜反思與限制

不確定就要留下記錄

  • 總時間可能不含冷卻或延長冷藏發酵。
  • 單位換算要保留原始值與依據。
  • 推定設備不能偽裝成來源明示。
  • 下一步應接上真實搜尋、擷取、驗證與 GitHub 寫入工具。
