# 作業反思

## Graph 相較單次 Prompt 的優點
把蒐集拆成 PLAN、SEARCH、FETCH、PARSE、NORMALIZE、VALIDATE、DEDUPLICATE 與 PERSIST，可以定位資料在哪個階段出錯。來源讀取失敗可回 SEARCH；格式錯誤可進 REPAIR，不必整份重做。

## 本次資料品質問題
- 各網站對總時間的定義不同，有些不包含完全冷卻或延長冷藏發酵。
- 設備有時未完整列出，從步驟推定時必須標記為推定。
- 「純素」標籤不代表每個替代商品都自動符合純素或無過敏原要求。
- 華氏與攝氏換算要保留原值，避免四捨五入造成誤差。

## 迴圈與檢查的價值
驗證失敗時，Graph 可依問題種類回 SEARCH、FETCH 或 REPAIR。設定重試上限可避免無限迴圈；超過上限保留 WARNING／FAIL，比自行猜測缺漏資料可靠。

## 改進方向
1. 為每個欄位保存來源證據片段與查閱日期。
2. 增加材料單位正規化，但區分重量、體積與匙量。
3. 增加重複食譜相似度比對與人工確認。
4. 將 LangGraph 範例接上真實搜尋、擷取與 GitHub API，再用測試案例驗證分支。

## 學習心得
Agent 的價值不只是生成答案，而是把來源、處理步驟、錯誤分支與品質檢查明確化。食譜少一項材料或錯一個溫度都可能讓成品失敗，因此「不確定就標記」比追求欄位全部填滿更可靠。
